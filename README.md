# SplitVpn

Windows-клиент для раздельного туннелирования: несколько VLESS/VMess/Trojan/SS-подключений
работают одновременно, а каждое приложение маршрутизируется в свой канал либо напрямую.

Приложение не реализует прокси-движок. Оно генерирует `config.json` и управляет процессом
**sing-box**, который делает всю сетевую работу: TUN-перехват, протоколы, сопоставление
по процессам, geoip/geosite.

## Что умеет

- Несколько одновременных туннелей. VLESS - прокси-протокол, а не L3-VPN, поэтому каналы
  не конкурируют за default route.
- Импорт `vless://`, `vmess://`, `trojan://`, `ss://`, `hysteria2://` - вставкой списка или подпиской.
  В окно импорта можно вставить и JSON-конфиг sing-box или Xray целиком; серверы кладутся
  в группу, которую вы назовёте (по умолчанию «Импортированные ссылки»).
- Подписки с автообновлением (интервал настраивается, по умолчанию 12 часов).
- Правила по имени процесса или полному пути к `.exe` -> канал / напрямую / блокировать.
- Правила по GeoIP, GeoSite, домену (точно, суффикс, вхождение, regex), IP/CIDR, порту.
- Переключение сервера внутри канала на лету через clash_api, без пересоздания TUN.
- Импорт правил маршрутизации из установленного Happ.

## Интерфейс

Fluent/WinUI-стиль на [WPF-UI](https://github.com/lepoco/wpfui) 4.3, окна `FluentWindow` с
Mica-подложкой. **Тема только тёмная и зафиксирована**: `ThemesDictionary Theme="Dark"` в
`App.xaml`, `SystemThemeWatcher` намеренно не подключается, поэтому переключение темы Windows
на приложение не влияет.

Серверы группируются по подпискам - и в списке, и в выпадающем списке канала; галка
«группировать по подпискам» над списком. Каждому потребителю выдаётся собственный
`ICollectionView`: общий `CollectionViewSource.GetDefaultView` заставил бы списки делить
`CurrentItem`.

Группы в списке серверов сворачиваются, состояние переживает перезапуск - имена свёрнутых
групп лежат в `CollapsedGroups` в `settings.json`. Обычной привязкой это не выражается:
ключ группы известен только внутри шаблона `GroupItem`, а индексатор с параметром-привязкой
XAML не поддерживает. Поэтому `Expander` связан с хранилищем через attached-свойства
`GroupExpander.Key` и `GroupExpander.Store`; хранилище передаётся привязкой, а не статикой,
чтобы состояние не утекало между окнами и тестами.

Имена серверов из подписок содержат эмодзи, поэтому шрифт задан списком с фолбэком
`Segoe UI, Segoe UI Emoji, Segoe UI Symbol`. WPF рисует эмодзи монохромными - цветные слои
COLR он не поддерживает, это ограничение платформы. Флаги стран Windows штатно показывает
парой букв (`PL`, `DE`), а не картинкой.

Две грабли WPF-UI, на которые это напоролось:

- `Style` без `BasedOn` подменяет дефолтный стиль контрола целиком, вместе с `ControlTemplate` -
  `ui:Button` превращается в обычную серую кнопку без иконки. При этом ключа
  `{x:Type ui:TextBlock}` в теме нет, так что и `BasedOn` не универсальное решение.
  Поэтому стилей для контролов WPF-UI в `App.xaml` нет, отступы задаются инлайном.
- `GridView` внутри `ListView` тема не оформляет - текст остаётся тёмным на тёмном.
  Списки собраны на `ListBox` с `DataTemplate`.

Значок - `src/SplitVpn/Assets/app.ico`, семь кадров (16-256px) в формате PNG внутри ICO.
Подключён и как `ApplicationIcon` (значок exe и ярлыка), и как `Resource` для `Window.Icon`
(панель задач). Перерисовывается генератором из `scratchpad` - исходник рисует вектор
и пакует ICO, растровых заготовок в репозитории нет.

## Трей и проверка доступности

Окно сворачивается и закрывается в область уведомлений (обе настройки отключаемы). При
закрытии в трей ядро продолжает работать - полный выход только через меню значка. Значок
берётся из WinForms: в WPF своего `NotifyIcon` нет, а WPF-UI убрал его в 4.x. Из-за этого
в проекте включён `UseWindowsForms`, но `System.Windows.Forms` убран из неявных using -
иначе он конфликтует с `System.Windows.Application`.

Проверка доступности идёт **не пингом**. ICMP тут бесполезен: VLESS и Hysteria2 - прокси
поверх TCP/QUIC, а хост может отвечать на ping при истёкшей подписке или отозванном ключе.
Вместо этого замер делает само ядро через clash_api:

```
GET /proxies/{tag}/delay?url=http://www.gstatic.com/generate_204&timeout=5000
```

Это HTTP-запрос сквозь туннель, то есть проверяется вся цепочка - сервер жив, ключ принят,
транспорт собран верно и трафик действительно ходит. Кнопка «Проверить все» меряет каждый
сервер (по 6 параллельно - каждый замер это реальный трафик), автопроверка по таймеру трогает
только выбранные серверы каналов, интервал настраивается, 0 отключает.

Имена в clash_api - это теги outbound'ов, а они переживают дедупликацию одинаковых названий.
Поэтому билдер возвращает соответствие `Id профиля -> tag` в `ConfigBuildResult`, и замер
адресуется точно, а не подбором по имени.

## Hysteria2

Поддерживается **нативно ядром**, без сайдкара - sing-box умеет `hysteria2`, если собран
с тегом `with_quic` (проверить: `sing-box version`). Источники: ссылки `hysteria2://` и `hy2://`,
JSON-конфиги sing-box и подписки в формате Xray.

Отдельно про формат Xray: там такие записи приходят как `"protocol": "hysteria"` с
`hysteriaSettings.version: 2`. Это **вендорское расширение** v2rayTun - стоковый Xray протокола
`hysteria` не знает вовсе, и сайдкар на нём не поднимется. Поэтому такие записи распознаются
и уводятся мимо Xray прямо в ядро:

```
"settings":       { "version": 2, "address": ..., "port": ... }
"hysteriaSettings": { "version": 2, "auth": ... }        ->  outbound type: hysteria2
"tlsSettings":    { "serverName", "alpn", "allowInsecure" }
```

Hysteria2 идёт поверх QUIC, поэтому транспорты v2ray и uTLS к нему неприменимы - в outbound
не попадают ни `transport`, ни `utls`, TLS всегда включён, `alpn` по умолчанию `h3`.

**Hysteria версии 1 не поддержана.** Формально ядро её умеет, но авторизация и обязательные
`up_mbps`/`down_mbps` там другие, а живого примера для проверки не было. Такие записи
помечаются в списке как неподдерживаемые - лучше честный отказ, чем сборка вслепую.

## Сайдкар Xray (XHTTP и балансировщики)

sing-box не умеет XHTTP - это транспорт Xray, его там нет на уровне кода. Не умеет он и
балансировщики провайдера (`routing.balancers` + `observatory`).

Когда подписка приходит **конфигами Xray**, каждый её элемент - это готовый рабочий конфиг
со своим `remarks`, набором хостов и балансировщиком. Переписывать его в термины sing-box
значит потерять и то, и другое, поэтому конфиг сохраняется целиком и запускается как есть
процессом `xray.exe`, а sing-box ходит в него через локальный SOCKS:

```
приложение -> TUN sing-box -> [правила] -> socks 127.0.0.1:N -> xray.exe -> сервер
```

Такую запись видно в списке как `имя (xray, N хостов, балансировка)`.

Детали, которые важны:

- **Правила маршрутизации провайдера вырезаются.** В конфигах они уводят часть доменов
  в `direct` мимо туннеля - при таком раскладе правила приложения врали бы. Маршрут решает
  sing-box; из конфига остаются только outbound'ы, балансировщик и observatory.
- **Сайдкар поднимается лишь под выбранный сервер канала.** Держать по процессу Xray на каждый
  сервер подписки расточительно, поэтому в режиме «авто» (urltest) серверы на Xray не участвуют -
  об этом пишется в журнал.
- **Соединения самого `xray.exe` выводятся из туннеля** отдельным правилом по пути процесса,
  иначе сайдкар заворачивает сам себя.
- **Серверы с XHTTP из обычных ссылок тоже работают.** Если транспорт умеет Xray, но не умеет
  sing-box, конфиг сайдкару синтезируется из исходной share-ссылки. Ссылка хранится в профиле
  целиком (`SourceLink`) намеренно: параметры вроде `mode` и `extra` модель не описывает,
  и сборка по разобранным полям молча теряла бы то, что серверу необходимо.
- Путь к `xray.exe` задаётся в настройках. Если не найден - проверяется комплект Happ, и об
  использовании чужого бинарника сообщается в журнал, без молчаливой подмены.

Протоколы, которых нет и в самом Xray (например `hysteria`), помечаются как неподдерживаемые.

## Модель: каналы

Правило маршрутизации указывает на **канал** (`VPN-A`, `VPN-B`), а не на конкретный сервер.
Какой сервер сейчас в канале - отдельная настройка. Поэтому обновление подписки, при котором
меняется список серверов, не ломает настроенную маршрутизацию.

В конфиге канал разворачивается в outbound типа `selector` (ручной выбор) или `urltest`
(галка «авто» - ядро само берёт быстрейший).

### Выбор канала сверяется с ядром

`default` у selector'а - не гарантия. С включённым `cache_file` sing-box хранит последний
выбор каждого selector'а в `cache.db` и при старте восстанавливает его **поверх** `default`.
Список серверов у всех каналов общий, поэтому после перезапуска (обновление подписки,
смена сервера, которую нельзя применить на лету) канал молча уезжал на сервер, выбранный
в нём когда-то раньше - вплоть до того, что весь трафик шёл через сервер, заведённый ради
одного сайта. Поэтому после запуска ядра приложение ждёт clash_api, читает `now` каждого
канала и, если он не совпадает с выбором в настройках, переключает через `PUT /proxies/<канал>`.
В журнале это строка `[канал] 'VPN-C': ядро восстановило 'X' из кеша, переключено на 'Y'`.

### Если выбранный сервер не попал в конфиг

Раньше в такой ситуации `default` не писался, и ядро брало первый outbound списка - какой
попадётся. Теперь порядок такой: сервер той же подписки (тот же провайдер), иначе прямое
соединение. Прямое соединение заметно сразу, чужой сервер - нет. Причина всегда пишется
в журнал и показывается в окне полосой «Конфиг собран с оговорками».

При обновлении подписки свежие серверы встают на место старых, а не в конец списка:
порядок групп и outbound'ов не перетасовывается.

Выбор каналов при обновлении снимается до замены серверов и возвращается после. Причина -
поведение WPF: ComboBox, чей выбранный объект пропал из ItemsSource, пишет в двустороннюю
привязку `null` ещё внутри `RemoveAt`, а свежий объект того же сервера появляется в списке
только потом. Раньше из-за этого канал после каждого обновления подписки оставался без
сервера; ядро маскировало это, восстанавливая прошлый выбор из `cache.db`, а после того как
выбор стал сверяться с настройками, канал честно уходил в прямое соединение. Пока список
перестраивается, реакция на смену выбора (сохранение, переключение на лету) отключена.

По той же причине заголовок группы новым серверам проставляется **до** вставки в список.
CollectionView без live shaping раскладывает элемент по группам один раз, при добавлении,
и смену `SubscriptionName` потом не замечает. Раньше заголовок выставлялся после вставки,
и после каждого обновления подписки её серверы висели в группе по умолчанию
(«Добавлено вручную») до перезапуска приложения. То же касается импорта ссылок с группой.

### Один экземпляр

Окно живёт в трее, и повторный запуск ярлыка раньше давал второй экземпляр: два ядра, два
набора сайдкаров, а у старого окна оставался чужой секрет clash_api. Теперь второй экземпляр
только поднимает окно первого (именованный mutex и событие в `Local\`).

## Порядок правил

sing-box применяет первое совпавшее правило. Генератор укладывает их так:

1. `sniff` и перехват DNS
2. приватные адреса -> напрямую
3. блокировка QUIC (если включена)
4. правила приложений - в порядке из таблицы
5. гео- и доменные правила - в порядке из таблицы
6. `final` - маршрут по умолчанию

Правила приложений всегда раньше гео: «этот процесс всегда через X» перевешивает
«домены такой-то страны напрямую». Внутри каждой таблицы порядок меняется кнопками
«Выше» / «Ниже».

## Форматы подписок

Поддерживаются: список share-ссылок, JSON-конфиг **sing-box**, JSON-конфиг **Xray**
(корень как объектом, так и массивом конфигов) и base64 от любого из перечисленного.
Clash YAML не поддерживается - распознаётся и сообщается явно, без попытки разобрать.
Тот же разбор работает в окне «Импорт ссылок».

Конфиг Xray с одним outbound на транспорте, который умеет sing-box (tcp/raw, ws, grpc,
httpupgrade, http), становится обычным профилем: без сайдкара сервер участвует в режиме
«авто» и в замерах ядра, а `xray.exe` для него не нужен. Всё, чего sing-box не тянет - XHTTP,
mKCP, HTTP-маскировка TCP (`header.type`), балансировщики, неизвестные поля `streamSettings`, -
по-прежнему уходит сайдкару целиком. `network: raw` (новое имя tcp в Xray) и
`realitySettings.password` (новое имя publicKey) распознаются.

Формат определяется так: сначала JSON, потом ссылки, потом YAML, потом base64 от всего этого.
Порядок именно такой, потому что в конфиге Xray попадаются поля вида `"email":"https..."` -
проверка на `://` принимала такой конфиг за список ссылок. Конфиги sing-box и Xray различаются
по содержимому `outbounds`: у первого элементы помечены `type`, у второго - `protocol`.

Диагностика ответа (HTTP-код, content-type, content-encoding, размер, использованный UA)
пишется в журнал - по ней видно, что именно вернул сервер.

Три подводных камня, на которые это напоролось на реальных провайдерах:

- `HttpClientHandler` по умолчанию идёт с `AutomaticDecompression = None`. Сервер отдаёт gzip,
  тело читается как текст, получается бинарный мусор. Флаг включён явно.
- **User-Agent решает всё, причём по-разному.** Одни панели выбирают по нему формат ответа
  (слова `clash` и `sing-box` переключают на YAML/JSON вместо ссылок), другие пускают только
  узнаваемые клиенты и на незнакомый UA отвечают `400 Device not supported`. Поэтому UA
  перебирается по списку, а сработавший запоминается в подписке (`UserAgent` в `settings.json`):
  часть панелей считает каждый запрос устройством и упирается в лимит подключений.
- **Причина отказа лежит в теле ответа, а не в коде.** `400 BadRequest` сам по себе не говорит
  ничего, а `{"message":"Device already connected"}` - говорит всё. Тело ошибки разбирается
  и попадает в журнал.

## Версии sing-box

В 1.12 сменились схема DNS-серверов (`address`-строка -> типизированный объект) и способ
отбрасывать трафик (outbound `block` -> route action `reject`). Генератор держит обе схемы и
выбирает ветку по выводу `sing-box version`. Кнопка «Проверить конфиг» прогоняет
`sing-box check` и показывает ошибки ядра дословно - это быстрее, чем гадать.

## Импорт из Happ

Кнопка «Из Happ» переносит из `%LocalAppData%\Happ`:

- гео-, доменные и IP-правила активного профиля из `routing.json`;
- process-правила из `config.json`.

**Серверы не переносятся.** Happ держит подписки в зашифрованном `subs.db`, а Xray получает
конфиг через stdin - учётные данные на диск открытым текстом не попадают. Ссылку подписки
нужно скопировать в интерфейсе Happ и добавить вручную.

Отдельная оговорка: наборы вида `geosite:ru-available-only-inside` - из списков runetfreedom,
в `sing-geosite` их нет. Импортёр такие правила добавляет **выключенными** и помечает в журнале;
в колонке «Свой rule-set URL» нужно указать прямую ссылку на `.srs` либо заменить набор.

## Geo-наборы качает приложение, а не ядро

Наборы объявлены в конфиге как `local` и лежат в `%AppData%\SplitVpn\core\rulesets\*.srs`.
Скачиванием занимается приложение ([RuleSetCache](src/SplitVpn/Services/RuleSetCache.cs)),
обновление раз в 7 дней.

Так сделано после двух подряд падений на старте. С `type: remote` ядро качает наборы само,
в момент запуска и через `download_detour`, и любая сетевая неудача убивает весь запуск:

```
FATAL start service: initialize rule-set: geoip-ru: ... EOF
FATAL start service: initialize rule-set: ... lookup <сервер>: context deadline exceeded
```

`sing-box check` такие ошибки не видит в принципе - он ничего не скачивает. С локальными
файлами запуск ядра офлайновый: нет файла - правило просто не попадает в конфиг с явным
предупреждением, а не роняет старт.

Если ядро уже запущено, приложение качает наборы через его локальный прокси
(`127.0.0.1:MixedPort`) - снаружи GitHub может быть закрыт.

## Журнал

Строки от ядра складываются в очередь, а в интерфейс отдаются пачками по таймеру (250 мс):
одна пересборка текста и одна запись в файл на пачку. Построчная отдача через
`Dispatcher.Invoke` с полной пересборкой буфера подвешивала окно намертво - на `log.level: info`
sing-box пишет каждый DNS-ответ и каждое соединение, до 70 строк в секунду.

Замер: 20 000 строк принимаются за 14 мс (0.0007 мс/строка), буфер держится на 600 строках,
UI-поток после всплеска отвечает за 0 мс.

По этой же причине уровень журнала ядра по умолчанию `warn`, а не `info` - настраивается
в блоке «Ядро и параметры». ANSI-раскраска из вывода ядра вычищается: в файле она была мусором.

## Конфликт туннелей

Два TUN-адаптера с `auto_route` одновременно делят таблицу маршрутов: чужой туннель
перехватывает в том числе прямые запросы ядра, и оно не может зарезолвить даже адрес
собственного сервера. В логе это выглядит как `lookup ...: context deadline exceeded`.

Поэтому наш адаптер называется `splitvpn-tun`, а перед подключением
[TunnelConflict](src/SplitVpn/Services/TunnelConflict.cs) ищет чужие активные туннели
(`sing-tun`, `wintun`, WireGuard, TAP) и предупреждает.

Имена наборов легко перепутать. Сверено с репозиториями: у geosite **нет** набора `ru`, российские
домены лежат в `category-ru` (есть ещё `category-gov-ru`); `geoip-private` тоже не существует -
приватные подсети покрыты правилом `ip_is_private`, которое строится всегда.

## Известные ограничения

- Ядро живёт только вместе с приложением: полный выход из трея его останавливает. Сделано
  намеренно - живой TUN без управляющего приложения ломает сеть.
- Правила по процессу не делят браузер: у него один процесс на все вкладки. Для разделения
  по сайтам нужны либо доменные правила, либо разные браузеры.
- Electron-приложения плодят дочерние процессы; надёжнее матчить по полному пути.
- Блокировка QUIC действует и на приложения, отправленные напрямую: правило стоит раньше
  правил приложений.
- Подписки в формате Clash YAML не поддерживаются - нужен список share-ссылок.
- Ограничение канала одной подпиской (`RestrictToSubscriptionId`) есть в модели, но в UI
  не выведено - правится в `settings.json`.
